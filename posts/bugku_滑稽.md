date: 2026-09-25

excerpt: 滑稽脸图片尾部拼了压缩包，改后缀解压拿到 flag。
---

思路：拿到附件是一张滑稽表情图，正常打开没问题，但一看体积就不对——这类表情图通常只有几十 KB，这张明显偏大。题目名就叫"滑稽"，也没有别的提示，那就先从"文件里是不是藏了东西"这个方向试。

问题：
1. 图片能正常显示，看不出任何异常，用肉眼看完全没线索。
2. 不确定是隐写还是文件拼接，一开始走了弯路，先去试了 StegSolve 翻颜色通道，翻了一圈什么都没有。
3. 用记事本打开看到一堆乱码，不知道从哪里开始有隐藏数据。

解决：
1. 先用 010 Editor 打开看十六进制，定位 PNG 的文件头 \x89PNG 和结束标记 IEND。正常 PNG 在 IEND 后面加 4 字节 CRC 就结束了，这张图 IEND 后面还跟了很长一段数据。
2. 把 IEND 后面的那段数据单独复制出来另存成文件，用 file 命令一看是 Zip archive data，说明后面直接拼了一个压缩包。
3. 按评论区说的更省事的做法：直接把图片后缀从 .png 改成 .zip，双击就能用压缩软件打开，里面直接就是 flag。
4. 交上去通过。

补充：
1. PNG 的结构是"8 字节签名 + 若干数据块 + IEND 结束块"，每个块都是「长度 + 类型 + 数据 + CRC」。只要解析到 IEND 就可以停了，后面多出来的字节不影响图片显示——这正是这类题能成立的原因。
2. 类似套路还有：图片后面拼 rar、拼 7z、拼另一个图片；有时还会被反过来用，比如把 zip 的文件头改掉伪装成图片。
3. 排查用的命令其实很简单：binwalk 文件名 先看有没有第二个文件系统/压缩流；foremost 或者 binwalk -e 做分离；最快的是 010 Editor 直接 Ctrl+F 搜 PK（zip 的文件头）。

工具：010 Editor、binwalk

踩坑记录：
1. 先跑 file 滑稽.png，输出就是 PNG image data，看不出后面拼了东西——file 只看文件头，不看文件尾。
2. 试过 binwalk -e 直接提取，可能是因为拼接的 zip 没有标准偏移特征，什么也没跑出来。
3. 又用 strings 捞了一遍，想着 flag 也许是明文；实际上 zip 里的内容是压缩过的，strings 捞不出来，白忙一场。
4. 最后是 010 Editor 手动找 IEND 标记才定位到拼接点，这一步反而最直接。

总结：这题的核心是"图片 + 压缩包"这种拼接题。识别方法有两种，一是看体积是否异常偏大，二是用 010 Editor 或者 binwalk 看有没有第二个文件头。以后遇到图片题，我打算按固定顺序排查：先看体积 → 再看文件尾有没有拼接 → 再看元数据 → 最后才是隐写通道，不要一上来就乱试工具。另外也记住一句：file 和 strings 这类工具只能给你"是不是有异常"的线索，不能给你"异常在哪里"，定位具体偏移还是得靠十六进制编辑器。
