title: SQL注入-宽字节注入
date: 2026-11-18
tags: [CTFHub, WEB, SQL注入, 编码]
excerpt: GBK 编码下用 %df 吃掉转义反斜杠，让 addslashes 的防护失效。
---

思路：后端用 addslashes 给引号加了反斜杠，直接把单引号逃逸掉是不可能的。但如果数据库连接用的是 GBK 这类双字节字符集，可以构造一个"半个汉字"把反斜杠吃进去，让引号重新露出来。

问题：
1. 引号一直被转义，试了很多 payload 都没用。
2. 不知道怎么判断字符集是 GBK 还是 UTF-8。
3. 知道了宽字节的概念，但不知道 ß 具体怎么和反斜杠拼在一起。

解决：
1. 先确认转义行为：传一个单引号，看页面返回的是 ' 还是直接报错，确认 addslashes 在工作。
2. 判断字符集：传 %df%27，如果页面把 %df%5c%27 当成一个 GBK 字符解析，就说明是 GBK 连接。
3. 构造：id=%df%27，%df 和反斜杠 0x5c 组成一个合法的 GBK 汉字，剩下的单引号逃逸出来。
4. 在逃逸出来的引号后面接常规注入语句，拿到数据，提交通过。

补充：
1. 宽字节注入成立的前提是：数据库连接的字符集是 GBK/GB2312 这类双字节编码，且 PHP 层用了 addslashes/magic_quotes 这种"加反斜杠"的方案。
2. 这是"字符集不一致"导致的经典漏洞：PHP 层按单字节处理，数据库按双字节处理，两边对同一个字节序列的理解不同。
3. 正确的修复不是把 addslashes 换成 mysql_real_escape_string，而是用参数化查询——参数永远不参与 SQL 词法分析，字符集怎么错都不会变成语法。

工具：Burp Suite、Python（辅助编码）

踩坑记录：
1. 一开始把 %df 写成了 %df%27%20，空格和引号的位置搞错，一直没生效。
2. 没有先确认字符集，拿 UTF-8 的环境试宽字节，当然无效。
3. Burp 里直接输入 %df 会被当成字面量，得在 Repeater 的 Hex 视图里改原始字节。

总结：宽字节注入是"编码差异"造成的漏洞，跟过滤强度无关——过滤做得再狠，只要转义逻辑和字符集理解不一致就有缝。这题也提醒我：看到 addslashes 不要急着下"安全"的结论，先看连接字符集。
