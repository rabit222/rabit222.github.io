excerpt: 注入点不在 URL 参数上，而在 Cookie 里，页面拿 cookie 值去查库。
---

思路：常规注入点在 GET/POST 参数上，这题的题目把数据来源换成了 Cookie：页面读 cookie 里的某个值，拼进 SQL 去查询。URL 里改参数没用，得改请求头。

问题：
1. 一直盯着 URL 参数试，完全没有回显变化。
2. 不知道注入点在哪儿，页面上也没有明显的输入框。
3. 知道要看请求头，但不清楚具体是哪个 cookie。

解决：
1. 用 Burp 抓完整请求，逐个改 Cookie 里的每一项，观察响应变化。
2. 找到会回显/影响查询的那一项，先测 id=1 和 id=1 and 1=2 的差异。
3. 确认注入点之后，按联合注入/布尔盲注的常规流程取数据。
4. 拿到数据，提交通过。

补充：
1. 注入点不止参数：Cookie、Referer、User-Agent、X-Forwarded-For 这些请求头经常被后端直接拼进 SQL 或日志，都可能成为注入点。
2. 这类题的价值在于提醒：做注入先看"数据从哪来"，而不是只盯地址栏。
3. Burp 的 Proxy History 里可以一眼看到所有请求头，比在浏览器里翻方便得多。

工具：Burp Suite（改请求头）、sqlmap（-r 读请求文件、--level 2 才检测 cookie）

踩坑记录：
1. 一开始只在浏览器地址栏改参数，当然没反应。
2. 不知道哪个 cookie 是注入点，挨个试花了点时间——其实看页面回显的 id 值就能反推。
3. sqlmap 默认 level 1 不检测 cookie，必须加 --level 2 或以上，第一次用的时候完全不知道这件事。

总结：注入点是"任何进入 SQL 的外部数据"，不再局限于 URL 参数。养成习惯：抓包之后把请求头挨个看一遍，尤其是有回显字段的地方。
