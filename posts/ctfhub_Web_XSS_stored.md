---
title: XSS-存储型
date: 2026-11-18
tags: [CTFHub, WEB, XSS]
excerpt: payload 存进数据库，任何人打开页面都会中招，比反射型更危险。
---

思路：存储型 XSS 的输入会被保存（评论、留言、昵称这类），然后被其他页面读出来渲染。特点是"打一次，长期有效"，不需要诱导点击特定链接。

问题：
1. 提交的 payload 在提交页看不到，以为没成功。
2. 不知道 payload 存到了哪里、会在哪个页面展示。
3. 提交后页面没弹窗，判断不了到底算不算成功。

解决：
1. 找到所有能提交内容的地方（留言板、昵称、个人简介），逐个提交探测字符串。
2. 提交后去"列表页/详情页"看输出位置，确认存储和回显都存在。
3. 构造 payload 再提交，打开列表页，弹窗即成功。
4. 用 onerror 这类不需要闭合 script 的写法，兼容性更好，提交通过。

补充：
1. 存储型 XSS 的危害面更大：所有访问该页面的用户都会执行，管理员后台尤其危险（可以配合 CSRF 做组合拳）。
2. 防御的核心是"输出编码"，不是"输入过滤"——同一个数据在不同上下文的编码方式不同。
3. 富文本场景下单纯过滤 <script> 没用，最终要靠 HTML 白名单过滤库（如 DOMPurify）。

工具：浏览器、Burp Suite

踩坑记录：
1. 提交页本身不回显，就以为注入失败，其实要去列表页看。
2. 试了几次都是"标签被转义"，说明存储时做了实体编码，换了 onerror 也不行——这一处是安全的，得换别的字段。
3. 列表页缓存了，刷新了几次才看到变化。

总结：存储型 XSS 验证要看"展示端"，而不是"提交端"。这题也让我第一次意识到：同一个站点的不同字段，防护程度可能完全不同，得逐个试。
