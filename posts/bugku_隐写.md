思路：附件是一张图，题目名直接就叫"隐写"，那方向很明确，就是把藏进去的数据抠出来。难点是不知道藏的方式。

问题：
1. 图片肉眼看着完全正常，没有多余的边角或者色块。
2. 不知道数据藏在文件尾、元数据、还是像素里。
3. 一开始乱试工具，StegSolve 翻了一遍通道没结果，浪费了不少时间。

解决：
1. 先用 010 Editor 看文件尾，IEND 后面干净，没有拼接的压缩包。
2. 用 exiftool 看元数据（EXIF / 注释字段），这类题目经常把内容藏在 Comment 里；这张图不是这条路。
3. 回到正规的隐写排查顺序，用 StegSolve 逐个通道、逐个位平面（bit plane）翻，同时试 LSB 提取，最后定位到数据藏在像素的低位里，提取出来就是内容。提交通过。

补充：
1. LSB 隐写的原理：把每个像素 RGB 的最低位拿来存数据。因为最低位变化对人眼来说只等于 1/255 的亮度差，完全看不出来。一个 1000x1000 的图，光是三个通道的最低位就能塞 375KB 数据。
2. 判断 LSB 有没有东西，除了 StegSolve 逐通道看，还可以看"位平面图"——如果最低位平面呈现明显的人工图案或者噪声异常，基本就有货。
3. 图片隐写的常见家族按排查顺序是：文件尾拼接 → 元数据（EXIF/Comment）→ LSB/通道 → 需要口令的 steghide/outguess → 调色板或 IDAT 块异常。每一类都有对应工具，顺序乱了就容易白忙。

工具：010 Editor、exiftool、StegSolve

踩坑记录：
1. 上来就用 StegSolve 翻通道，翻了一圈没结果，时间全浪费了。
2. exiftool 看元数据，Comment 字段是空的，这条路也断了。
3. binwalk 扫了一遍，没有嵌套文件，说明不是拼接题。
4. 最后回到位平面（bit plane）逐层看才发现数据藏在低位里。教训是：隐写题一定要按排查顺序走，不能一上来就凭感觉挑工具。

总结：这题最大的收获不是结论，而是排查顺序。我现在的固定流程是：看体积 → 看文件尾有没有拼接 → 看元数据 → 看颜色通道和位平面 → 最后再考虑需要密码的隐写（steghide 那种）。按顺序走，不会像一开始那样东试一下西试一下。另外也理解了 LSB 隐写的原理：把每个像素最低位拿来存数据，肉眼看颜色几乎没差别，所以这类题目靠"看"是永远看不出来的，必须用工具逐位分析。
