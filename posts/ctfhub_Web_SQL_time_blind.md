title: SQL注入-时间盲注
date: 2026-11-18
tags: [CTFHub, WEB, SQL注入, 盲注]
excerpt: 页面连"有数据/没数据"都不给了，只能靠 sleep() 的响应时间差判断真假。
---

思路：这题比布尔盲注更狠，页面返回的内容完全一样，不管查询成功还是失败都是同一个页面。唯一还能利用的信号是响应时间：让条件成立时数据库睡 5 秒，不成立时立刻返回，用耗时差当 True/False。

问题：
1. 页面完全没差别，一开始根本找不到判断依据。
2. 想到了 sleep()，但不知道该怎么把它塞进一个布尔表达式里。
3. 网络抖动会让 0.5 秒的延迟判断出错，不清楚阈值定多少合适。

解决：
1. 构造条件表达式：id=1 and if(1=1,sleep(5),0)，观察响应时间明显变长；换成 if(1=2,sleep(5),0) 立刻返回。通道确认。
2. 把真实条件套进去：id=1 and if(ascii(substr(database(),1,1))>100,sleep(5),0)，用响应时间二分。
3. 阈值定在 3 秒（sleep 5 秒，正常响应都在 1 秒内），先用几个已知答案为真/为假的请求标定一遍基线。
4. 写脚本循环，每个字符二分，拿到库名、表名、数据，提交通过。

补充：
1. 除了 if()，还能用 case when ... then sleep(5) else 0 end，效果一样。
2. sleep() 在部分环境被禁用（比如开了 safe 模式或权限受限），可换成 benchmark(10000000,md5('a')) 制造延迟。
3. 盲注要先测误差：同一个请求连发三次看耗时波动，波动大就加大 sleep 值或加重试逻辑。
4. sqlmap 的 --technique=T 就是这套逻辑，理解之后看它的输出会清楚很多。

工具：Python + requests（测时间）、Burp Suite（单个请求复现）

踩坑记录：
1. 一开始把 sleep 放在外层而不是 if 里面，导致条件真假都会睡，通道彻底失效。
2. 阈值定太紧（1 秒），网络抖动时误判过两次，差点以为脚本写错了。
3. 忘了关掉脚本里的并发，多个请求同时发出去，响应时间完全乱了，改成串行之后才准。

总结：时间盲注是"把信息通道压缩到只剩时间维度"。它比布尔盲注慢、比布尔盲注脆，但对环境的要求最低——只要页面还能返回，就能问问题。真正难的是脚本工程：超时、重试、基线标定，缺一不可。
