title: Pikachu-CSRF
date: 2026-11-23
tags: [Pikachu, WEB, CSRF]
excerpt: 用户已登录的情况下，伪造请求替他改资料。
---

思路：CSRF 的前提是"受害者已登录且浏览器会自动带 cookie"。攻击者构造一个页面，让受害者的浏览器在不知情的情况下发出改资料的请求。

问题：
1. 不理解为什么"请求伪造"能成功。
2. 不知道 GET 型和 POST 型的区别。
3. token 防护的那关卡住。

解决：
1. 先正常登录，抓一次修改资料的请求，看它带什么参数、什么 cookie。
2. GET 型：把修改资料的 URL 直接做成图片或者链接，让受害者打开就触发。
3. POST 型：写一个自动提交的 HTML 表单，诱导受害者访问。
4. token 型：这关有 token，单靠伪造请求过不去，需要配合 XSS 先读取 token。
5. 改掉资料里的信息，验证成功，提交通过。

补充：
1. 防御的核心是"校验来源 + token"：token 要绑定会话且一次性，SameSite cookie 也能挡住大部分场景。
2. CSRF 和 XSS 经常组合使用：XSS 拿 token，CSRF 发请求。
3. 真实场景里 CSRF 的价值取决于"那个操作有多敏感"，改密码、转账才是高价值目标。

工具：浏览器、Burp Suite、自建 HTML 页面

踩坑记录：
1. 一开始没登录就去伪造请求，当然失败——CSRF 依赖已登录的会话。
2. POST 表单的字段名写错，服务端收不到参数。
3. 以为 token 关也能硬打，其实必须先拿到合法 token。

总结：CSRF 的核心是"浏览器自动带凭证"这个机制。理解之后，防御思路也清晰了：要么让浏览器不自动带（SameSite），要么让凭证不可预测（token）。
