思路：这一关服务端加了校验（比如连续失败后拒绝），但防护强度不够：可能是只记录失败次数、没有锁定，或者拒绝逻辑可以被绕过。

问题：
1. 请求连续失败几次后开始被拒绝。
2. 不知道是限速还是锁定。
3. 放慢之后还是失败，怀疑判断逻辑有问题。

解决：
1. 先用小字典测：连续发 5 次，看第几次开始变。
2. 观察响应差异：是同一个页面，还是换了提示，或者直接 403。
3. 如果是限速，把请求间隔调大（比如 1~2 秒）再跑。
4. 如果是按 IP 封，换 X-Forwarded-For 或者走代理池。
5. 拿到正确密码，提交通过。

补充：
1. 常见的弱防护：只在前端限速、失败计数存在 cookie 里、封禁时间很短。
2. 防御侧的正确做法：服务端计数 + 账号锁定 + 验证码 + 多因素。
3. 判断"限速"还是"锁定"：看换一个账号是否还能尝试。

工具：Burp Suite Intruder（可设请求间隔）、Python 脚本

踩坑记录：
1. 一开始以为是账号被锁，换了个用户名还能试，才确认是 IP 限速。
2. Intruder 的 throttling 没开，请求发太快一直被拒。
3. 被拒之后的响应也有区别，一开始没细看，误判成"密码全错"。

总结：这题的价值是让我第一次区分"限速"和"锁定"——一个针对来源，一个针对账号，绕过思路完全不同。
