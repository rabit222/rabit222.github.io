---

思路：Pikachu 的暴力破解模块给了四种场景：表单无防护、客户端校验、服务端校验、token 校验。核心不是"跑字典"，而是先判断防护在哪一层，再决定用什么工具。

问题：
1. 一开始直接开 Burp 的 Intruder 跑字典，结果被拦或者一直报错。
2. 分不清页面上的"错得太快"和"真的被校验了"。
3. token 场景下每次请求都要换，手工不可能。

解决：
1. bf_form：没有任何防护，Burp Intruder 加载用户名字典和密码字典，按响应长度差异找出成功的那一条。
2. bf_client：防护只在前端 JS，用 Burp 截包后直接改密码字段，或者删掉 JS 校验再提交。
3. bf_server：服务端只做简单校验（比如限制频率），换代理池或者放慢请求间隔就能过。
4. bf_token：token 一次性，需要写脚本先 GET 页面取 token、再带着 token 提交，循环跑。
5. 找到正确的账号密码，登录成功，提交通过。

补充：
1. 判断防护位置的办法：抓包看请求里有没有 JS 生成的字段、看响应有没有"密码错误"之外的提示。
2. 真实环境还要考虑：账号锁定、验证码、频率限制、IP 封禁，这些都不是"跑字典"能解决的。
3. 防御：服务端限速 + 验证码 + 账号锁定 + 强密码策略，多因素结合才有效。

工具：Burp Suite Intruder、Python 脚本、hydra

踩坑记录：
1. 一开始没分类，直接对四个场景全用同一个方法，白跑。
2. 字典加载时用户名和密码搞混了，Intruder 里 cluster bomb 的 payload 位置设错。
3. token 场景下忘了先取 token，请求一直返回"非法请求"。

总结：暴力破解题的顺序是"先找防护层，再选工具"。前端校验靠改包，服务端校验靠限速绕过，token 靠脚本自动化——三种情况思路完全不同。
